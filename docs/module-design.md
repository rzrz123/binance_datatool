# 模块与接口设计

> 目标: 改动能被人类快速审计 / review. 格式细节见 [python-style.md](python-style.md); 模块职责边界见 [AGENTS.md](../AGENTS.md).

写代码, 加功能时优先遵守本文. 核心原则: **小接口, 深实现** — 调用方少学东西, review 少盯表面.

## 少造表面, 多往里塞

- **默认改现有入口**, 不平行新开公开函数 / helper / 文件.
- **禁止为单次调用抽函数**: 只在一处用到的逻辑, 留在调用处或塞进已有深函数; 不要为「看起来干净」再包一层 `_helper`. 出现真实复用, 或抽出后调用方明显更好审时再抽.
- 新建之前问: 删掉它之后, 复杂度是消失了, 还是散到多个调用点? 后者才值得存在.
- 一次改动尽量少动公开接口; 行为变化集中在少数深函数里, 而不是摊到很多薄包装.

## 接口统一: 同一件事一条路

- 同类能力共用同一签名形状: 参数名, 返回值形态, 错误方式一致.
- 禁止为「这次方便」另起一套 (`foo` / `foo_v2` / `foo_ex`).
- 新逻辑放到职责对应的模块里, 不跨层偷懒, 也不在调用方复制实现.

## Optional args 吃差异

用可选参数 / 默认值扩展现有入口, **旧调用零改动**:

```python
# ✅ 同一入口吞掉变体
def load_data(factor_list: list[str], symbols: list[str] | None = None) -> pd.DataFrame:

def playback_single(self, plot: bool = True, show_symbol: bool = True) -> tuple[...]:

# ❌ 为变体再开公开函数
def load_data_for_symbols(...): ...
def playback_single_no_plot(...): ...
```

可选参数只表达「少数调用需要的旋钮」. 不要把内部步骤全部暴露成参数; 分支, 解析, 兼容, 回退留在函数内部.

## 复杂度放进实现

- 调用方只关心: 传什么, 拿什么, 有什么不变式.
- 实现可以长; 用现有分段注释习惯标清步骤 (`# ===`, `# 1. ...`).
- Review 优先看 **公开签名 + 调用点**; 实现细节应被接口挡住, 而不是泄漏到每个调用方.

```
┌─────────────────────┐
│   小接口            │  ← 少方法, 参数简单, 默认值稳妥
├─────────────────────┤
│                     │
│   深实现            │  ← 分支 / 兼容 / 细节藏在这里
│                     │
└─────────────────────┘
```

## 为人类 review 做事

| 做 | 不做 |
|----|------|
| 扩展现有入口 (默认参数 / 内部分支) | 顺手抽一堆薄 helper |
| 行为变化集中在一两个深函数 | 同一逻辑复制到多处 |
| 命名直接对应业务 | 空洞抽象名 (`process`, `handle`, `Manager`) |
| 保持模块边界清晰 | 为「干净」引入用不上的基类 / Protocol / 新抽象层 |

## 自检 (改完问自己)

1. 能不能只改一个现有函数就完成, 而不是新增公开表面?
2. 新参数是否有合理默认值, 旧调用是否不用改?
3. 调用方是否仍只依赖少量事实 (签名 + 不变式), 而不是实现细节?
4. 另一个人只看 diff 的公开接口和调用点, 能否判断行为变了什么?
